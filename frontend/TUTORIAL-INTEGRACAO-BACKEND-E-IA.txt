SGS BARBER — TUTORIAL DE INTEGRAÇÃO
====================================
Versão: Front-end completo + contratos para Backend, Banco de Dados e IA

IMPORTANTE
----------
Este projeto contém SOMENTE o FRONT-END.

Não existe neste pacote:
- banco de dados real;
- servidor backend real;
- API de IA real;
- chave de OpenAI/Gemini/Anthropic ou outra IA;
- automação real de WhatsApp;
- pagamento real.

O front-end funciona em modo demonstração usando localStorage.
Quando o backend estiver pronto, config.js deve ser alterado para USE_API=true.

OBJETIVO DA EQUIPE
------------------
A arquitetura foi pensada assim:

CLIENTE / BARBEIRO
        |
        v
HTML + CSS + app.js
        |
        v
api.js (Store)
        |
        v
BACKEND REST
        |
        +------> BANCO DE DADOS
        |
        +------> SERVIÇO DE IA (quando necessário)
        |
        +------> WhatsApp / calendário / pagamentos futuros

O front-end NÃO deve acessar o banco diretamente.
O front-end NÃO deve guardar segredo ou chave de IA.
O backend deve validar tudo novamente, principalmente disponibilidade de horário,
permissões, autenticação e valores financeiros.

- financeiro geral
- serviços

4. AGENDAMENTO — REGRA MAIS IMPORTANTE
============================================================

O front mostra horários possíveis, mas o backend é a AUTORIDADE FINAL.

Endpoint recomendado:

GET /api/availability?barberId=1001&serviceId=3&date=2026-10-02

Resposta sugerida:

{
  "barberId": 1001,
  "serviceId": 3,
  "date": "2026-10-02",
  "slots": [
    {"time":"08:00","available":true},
    {"time":"08:30","available":false,"reason":"booked"},
    {"time":"09:00","available":true}
  ]
}

O backend deve considerar:
- expediente do barbeiro;
- dia de folga;
- férias;
- intervalo;
- bloqueios;
- duração do serviço;
- buffer;
- agendamentos existentes;
- status cancelado/no-show;
- antecedência mínima, se configurada.

Ao criar a reserva:

POST /api/appointments

O backend deve verificar a disponibilidade NOVAMENTE dentro da transação.

Nunca confiar apenas no horário enviado pelo front-end.

============================================================
5. FLUXO DO CLIENTE
============================================================

O fluxo atual é:

1. escolher barbeiro
2. abrir perfil do barbeiro
3. escolher/favoritar barbeiro
4. escolher serviço
5. escolher data
6. consultar disponibilidade
7. escolher horário
8. informar dados
9. confirmar
10. salvar no calendário ou abrir WhatsApp

O front não deve permitir que a seleção de serviço apareça antes do barbeiro.

O endpoint de serviços pode retornar todos, mas o front usa serviceIds do
barbeiro para mostrar somente os serviços vinculados.

============================================================
8. AVALIAÇÕES
============================================================

A avaliação só deve ser liberada depois que o atendimento estiver concluído.

POST /api/ratings

Body:
{
  "appointmentId": 123,
  "shopRating": 5,
  "barberRating": 5,
  "comment": "Excelente atendimento"
}

Regras do backend:
- appointmentId deve pertencer ao cliente autenticado;
- appointment deve estar concluído;
- não permitir avaliação duplicada;
- barberId deve vir do atendimento, não ser confiado ao cliente;
- validar nota entre 1 e 5.

GET /api/barbers/{id}/ratings

Resposta pode conter:
- avaliações
- média
- quantidade

============================================================
11. COMANDA E FECHAMENTO
============================================================

O front possui uma tela de fechamento.

Fluxo:
- selecionar atendimento aberto;
- aplicar desconto;
- escolher forma de pagamento;
- registrar observação;
- finalizar atendimento.

Endpoint recomendado:

POST /api/appointments/{id}/checkout

Body:
{
  "discount": 0,
  "paymentMethod": "PIX",
  "note": ""
}

O backend deve calcular o total final.

Fórmula:
finalTotal = servicePrice + extrasTotal - discount

Nunca confiar no finalTotal enviado pelo navegador.

Ao concluir:
- status = Concluído
- completed_at = agora
- registrar pagamento
- atualizar estoque dos produtos vendidos
- calcular comissão conforme regra cadastrada
- gerar notificação

Idealmente tudo isso deve ocorrer em uma transação de banco.

============================================================
12. PRODUTOS E ESTOQUE
============================================================

Produtos adicionados à comanda devem gerar registros em appointment_products.

POST /api/appointments/{id}/products

Body:
{
  "productId": 101,
  "quantity": 1
}

O backend deve:
- conferir estoque;
- impedir estoque negativo;
- registrar preço praticado no momento da venda;
- diminuir estoque;
- incluir o produto no total.

Não usar somente o preço atual do produto para reconstruir vendas antigas.

============================================================
15. BUFFER ENTRE ATENDIMENTOS
============================================================

Exemplo:

Buffer: 10 minutos

Reserva às 14:00:
14:00 → 14:30 atendimento
14:30 → 14:40 preparação

Próximo horário permitido: 14:40 ou o próximo slot da grade.

O backend deve aplicar o buffer na verificação de conflito.

É recomendado armazenar start_time e end_time efetivos no appointment.

============================================================
19. IA — RESPONSABILIDADE DO DESENVOLVEDOR DE IA/BACKEND
============================================================

A aba IA do front é SOMENTE um placeholder.

A IA deve ser conectada pelo BACKEND.

Arquitetura:

Frontend
   |
   | POST /api/ai/chat
   v
Backend
   |
   | chave secreta
   v
Provedor de IA

Nunca:

Frontend -> API da IA usando chave secreta

Endpoint sugerido:

POST /api/ai/chat

Body:
{
  "message": "Crie uma mensagem de retorno para um cliente que não vem há 60 dias",
  "context": {
    "clientId": 10,
    "purpose": "reactivation"
  }
}

Resposta:
{
  "message": "Olá, Lucas...",
  "provider": "..."
}

O backend deve:
- validar usuário;
- limitar uso;
- proteger chave da IA;
- registrar logs quando necessário;
- filtrar dados sensíveis;
- impedir que o cliente acesse informações de outros clientes;
- controlar custos/tokens;
- tratar erros e timeout.

22. CORS E AMBIENTE
============================================================

Durante desenvolvimento:
- permitir apenas a origem do front definida pela equipe;
- não usar CORS aberto para produção.

Exemplo de configuração do front:

config.js

USE_API: true
API_BASE_URL: "https://api.seudominio.com"

Em desenvolvimento:

API_BASE_URL: "http://localhost:3000"

O backend deve aceitar JSON e responder corretamente com HTTP status.

200 = consulta/alteração realizada
201 = criação realizada
204 = exclusão sem conteúdo
400 = dados inválidos
401 = não autenticado
403 = sem permissão
404 = não encontrado
409 = conflito, principalmente horário ocupado
422 = regra de validação
500 = erro interno

============================================================
23. ERROS IMPORTANTES QUE O BACKEND DEVE TRATAR
============================================================

Conflito de horário:
HTTP 409

Exemplo:
{
  "error": "APPOINTMENT_CONFLICT",
  "message": "Este horário acabou de ser reservado."
}

O front deve mostrar uma mensagem e atualizar a disponibilidade.

Barbeiro inativo:
Não permitir nova reserva.

Serviço inativo:
Não permitir nova reserva.

Serviço não vinculado ao barbeiro:
Não permitir nova reserva.

Data de folga:
Não permitir reserva.

Fora do expediente:
Não permitir reserva.

Buffer incompatível:
Não permitir reserva.

Cliente tentando avaliar atendimento de outra pessoa:
HTTP 403.
